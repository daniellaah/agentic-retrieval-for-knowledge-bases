# 索引重复处理开销：测量记录

以下首先记录第 1–2 项完成后、执行第 3–5 项之前的基线。第 3–5 项随后按代码简化范围完成，结果见文末“清理后的复测”。generation 继续作为独立模块保留。

## 方法与范围

- 环境：macOS-26.6.2-arm64-arm-64bit-Mach-O，Python 3.13.5，SQLite 3.47.1，NumPy 2.5.2，qdrant-client 1.19.0。
- 每份合成文档生成一个 chunk，全部 embedding 输入互不相同；向量维度为 1,024，随机种子为 7，batch size 为 32。
- 使用临时 SQLite 文件及 Qdrant Local `:memory:`；不访问用户笔记、现有索引或外部服务。SQLite 为 WAL，synchronous=FULL，wal_autocheckpoint=1000。
- 向量预先生成，用合成响应替代模型调用；保留现有嵌入校验、缓存、索引写入和发布流程。文件扫描、向量预生成、启动导入和测试环境初始化不计时。
- 每种规模独立重复三次，使用未插入计时探针的运行统计整体耗时。另做一次带探针的运行记录调用次数和耗时分布。
- 探针的 inclusive 时间包含子调用，不能将这些数字直接相加；SQL 时间只覆盖 execute，后续取行/解码仍计入调用函数。
- 本结果反映当前本地索引处理成本，不能替代真实模型延迟、Qdrant Server 网络或 ANN 索引构建测试；不能直接当作优化后的预计提速。

复现命令（输出文件须不存在）：

```sh
uv run --locked python -B benchmarks/profile_indexing.py --output /tmp/indexing-overhead-new.json
```

脚本：[profile_indexing.py](profile_indexing.py)；原始结果：[indexing-overhead.json](indexing-overhead.json)。结果包含源文件 SHA-256、每次耗时、调用次数和调用关系。

## 未插入探针的实际耗时

| Chunk 数 | 首次构建 | 缓存重建（force） | 无变更重用 |
| --- | ---: | ---: | ---: |
| 256 | 0.173 秒 | 0.166 秒 | 0.052 秒 |
| 2,048 | 1.372 秒 | 1.346 秒 | 0.422 秒 |

表中为三次运行的中位数。首次构建的“模型”只返回预生成向量，因此它与缓存重建的差距不能解释为真实 embedding 缓存收益。缓存重建和无变更重用都没有模型调用。

## 2,048 个 chunk 的重复工作

| 项目 | 首次构建 | 缓存重建 | 无变更重用 |
| --- | ---: | ---: | ---: |
| 缓存读取/校验调用 | 8,192 | 8,192 | 2,048 |
| 完整记录加载 | 2 | 3 | 2 |
| 记录与向量整批加载 | 2 | 2 | 1 |
| 事务提交 | 2,115 | 2,051 | 0 |

缓存重建的 8,192 次 get_embedding 调用分布为：检查缺失输入 2,048 次、add_chunk 2,048 次、候选 load_snapshot 2,048 次、publish 内部 load_snapshot 2,048 次。

缓存重建还读取一次旧版本记录用于文档变更统计，因此 snapshot_records 共执行三次；无变更路径也先读旧记录，再随 load_snapshot 读一次。

缓存重建的 2,051 次提交中，2,048 次来自逐 chunk 写入，另外三次来自候选创建、保存后端元数据和发布。

## 开销归因与判断

缓存重建的探针运行耗时为 1.375 秒；未插入探针的中位数为 1.346 秒。各项如下，存在包含关系：

| 项目 | 探针测得耗时 | 解释 |
| --- | ---: | --- |
| 缓存读取函数合计 | 271.9 毫秒 | 约占探针运行的 19.8%；包含键计算、取行、校验和向量处理 |
| 其中缓存 SELECT execute | 37.1 毫秒 | 已包含在上一行，不可重复相加 |
| 快照记录加载合计 | 111.4 毫秒 | 包括旧版本一次和候选两次反序列化/身份校验 |
| COMMIT execute 合计 | 102.6 毫秒 | 约占探针运行的 7.5%，并非全部事务成本 |
| Qdrant Local upsert | 517.8 毫秒 | 是当前流程的大项，但不能用于推断 Server 性能 |
| Qdrant 全量核验 | 167.7 毫秒 | 承担发布前数据完整性检查 |

这说明重复工作确实存在，但“缓存查询慢”不能全部归因于 SQLite 查询本身。减少重复键计算、向量读取及校验，比只减少 execute 次数更值得评估。批量写入也有可测的收益空间，但不能据此承诺消除所有提交耗时。

无变更重用仍包含 Qdrant 全量核验，因此它不是常数时间操作。在这个样本中该核验约为 169 毫秒，保留它可以发现远端点、payload 或向量被改动。

## 清理后的复测

本轮以减少重复代码和废弃接口为目标，没有引入缓存复用、批量事务、新配置或抽象层。索引仅将用于变更统计的旧记录读取移到确定需要重建之后；publish 和 Qdrant 的完整性核验保持原样。

context 移除了未被产品逻辑使用的 citation_map 属性，并统一通过 citation_sources 输出诊断证据，删除重复的 evidence_blocks、citation_map JSON 字段。Python 内部的 EvidenceBlock 及全部来源信息保留。评估清除了重复携带同一搜索函数的多后端结构；CLI 移除了空的资源管理层；README 合并了重复说明。现有评估能力和独立 generation 模块保留。

生产代码净减少 23 行、一个属性访问器，没有新增类、函数、生产模块或依赖。

使用相同脚本、参数和三次运行中位数，2,048 个 chunk 的结果为：

| 场景 | 清理前 | 清理后 |
| --- | ---: | ---: |
| 首次构建 | 1.372 秒 | 1.396 秒 |
| 缓存重建 | 1.346 秒 | 1.368 秒 |
| 无变更重用 | 0.422 秒 | 0.388 秒 |

无变更路径的完整记录加载从两次减到一次；缓存读取仍为 2,048 次。缓存重建的读取次数、快照加载次数和事务提交次数均未改变。首次构建和缓存重建的耗时约相差 1.7% 和 1.6%；这些是先后两轮小样本测量，不将该幅度的差异解释为稳定性能变化。未观察到明显退化，也不以提速作为本次清理的验收目标。

全量测试从 433 项通过变为 435 项通过，服务测试仍有 37 项跳过：新增三个无变更路径的损坏检测用例，删除一个重复的 CLI 参数用例。安装后的旧索引兼容性核对通过；除明确移除的两个诊断字段外，记录、向量、身份、排名、模型请求、context_id 和模拟生成结果与旧固定样本一致。
